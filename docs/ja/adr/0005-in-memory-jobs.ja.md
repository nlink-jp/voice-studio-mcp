# ADR-0005: 非同期ジョブは in-memory のみ(永続化しない)

- **Status**: Accepted (2026-07-04)

## Context

`synthesize_script` は長時間走るため、ツール呼び出しとしては job_id を即時
返却し `check_job` でポーリングさせる非同期設計が必要。問題はサーバー再起動
(MCP クライアントの再接続、マシン再起動)をまたぐジョブの扱いである。
ジョブ永続化はステートマシンの復元・孤児ジョブの再開・多重実行防止など
複雑さが大きい。

## Decision

ジョブテーブルは in-memory のみとし、永続化しない。

- 再起動後の `check_job` は `job_not_found` を返すが、そのエラーメッセージに
  **回復手順を明記**する:「ジョブは再起動で失われる。`synthesize_script` を
  再実行すればキャッシュ(ADR-0004)により未完了行だけが合成される」。
- ジョブは server-lifetime context で実行し、SIGTERM 時は残行を中断して
  state=failed(fatal_error に同じ回復ガイダンス)で終える。
- 完了ジョブは最大 32 件保持し、最古から evict。
- 全ジョブは共有セマフォ(`synthesis.concurrency`、既定 1)配下で走り、
  並行ジョブでもエンジン負荷は一定に抑える。

## Consequences

- 実装が単純で、復元バグの類が構造的に存在しない。
- 「回復はエージェントの再実行」という設計は、ツール利用者が自律エージェント
  であることに依存する(エラーメッセージの文言品質が UX の要)。
- 数時間規模の長編でサーバーが落ちた場合も、失うのは進行状況の表示だけで、
  合成済み行はキャッシュに残っている。

## Alternatives considered

- **ジョブのディスク永続化+再開**: 複雑さに対しリターンが小さい
  (キャッシュがあるため「再開」と「再実行」のコスト差がほぼない)。不採用。
- **同期実行(チャンク分割)**: MCP クライアントのタイムアウトに縛られ、
  長編で破綻する。不採用。
