# ADR-0010: エージェントが用意した作業場所で voice-studio が仕事をする

- **Status**: Accepted (2026-07-05)
- **経緯**: [Issue #1](https://github.com/nlink-jp/voice-studio-mcp/issues/1) の3案の議論から確定

## Context

本サーバーの契約は「入力(台本・casting)はワークスペース内のファイル、
出力もファイルパス返し」であり、エージェントとサーバーが無制限のファイル
システムビューを共有することを暗黙の前提にしていた。MCP クライアントの
ファイルアクセスがサンドボックス化されるとこの前提が壊れる:

- **クラス A(同一 FS + 書き込み制限)**: Claude Code ローカルサンドボックス
  等。書き込み許可域は通常プロジェクトディレクトリ+tmp のみで、既定の
  `~/.voice-studio` に台本を書けない。
- **クラス B(FS 非共有)**: VM/コンテナ実行型クライアント。ファイル
  ハンドオフ自体が成立しない。

加えて、Desktop 級ホストは MCP サーバーをアプリ起動時にグローバル設定から
1度だけ起動し、**1プロセスが複数の並行会話にサービスし得る**。ワークスペース
の場所は起動時設定でなく **MCP セッションの中を通って**伝わる必要がある。
また、ステートフル+ファイル介在型の契約はツール Description だけでは
説明しきれず、同梱スキル(ADR-0009)を持たないクライアントは手探りになる。

## Decision

原則を一行で: **「エージェントが用意した作業場所で、voice-studio が仕事を
する」**。これを最小の機構で実装する。

1. **オプショナルな `workspace_root` パラメータ**(全ワークスペース系
   ツール): エージェントが自分の書き込み可能領域に mkdir したディレクトリの
   絶対パス。それが「用意」のすべてで、専用ツール・マーカー・GUID は
   持たない。省略時は従来の既定ルート(完全後方互換)。検証は
   「絶対パス・実在・ディレクトリ」のみ。レイアウト
   `<workspace_root>/<workspace_id>/…` は不変(1ルート複数作品を維持)。
   コール単位のステートレスなパラメータとする(1プロセス複数会話のため、
   サーバー側セッション状態にはしない — ADR-0005 と同思想)。
2. **`os.Root` によるカーネル強制の封じ込め(必須)**: エージェントが
   書ける場所でサーバーが仕事をする以上、ワークスペース内に植えられた
   symlink は「サンドボックス外をサーバーに読み書きさせる」confused-deputy
   昇格になる(旧設計では"エージェントはワークスペースに書けない"ことが
   隠れた保護だった — この反転が本 ADR の安全上の核心)。サーバーの
   ワークスペース内 I/O はすべて `os.Root` 経由とし、ルート外への symlink は
   カーネル境界で失敗して `path_not_allowed` にマップされる。
   `ResolveInside` は親切なエラーのための字句事前検査として存置。
   - **ffmpeg の残余ギャップ**: 外部プロセスは os.Root を継承できない。
     spawn 直前に全入力を `os.Root` の Lstat で「実在する通常ファイル」と
     再検証する。検証〜spawn 間の競合窓は、脅威モデル(ローカル・シングル
     ユーザー・混乱したエージェント)を根拠に許容する。
   - Go 下限を 1.25 に引き上げ(`os.Root` 自体は 1.24 導入、1.25 の
     ReadFile/WriteFile/MkdirAll/RemoveAll/Rename が実装に必要)。
3. **自己記述**: `get_usage` ツールがワークスペースモデル・制作フロー・
   台本スキーマ・復旧表を返し(go:embed した markdown、整合性テストで
   ツール名/エラーコード/スキーマと束ねる)、initialize の `instructions`
   フィールドで発見可能にする。

クラス B は引き続き**明示的スコープ外**(出力の消費者はホスト上の人間で
あるため実害は入力面に限られるが、単一データ経路の維持を優先)。

## Consequences

- クラス A が解決: エージェントはプロジェクトディレクトリ内に workspace を
  作り、全ツールに同じ `workspace_root` を渡すだけ。台本・casting が
  プロジェクトの成果物としてコミット可能になる副次効果もある。
- ツール数 7→8(get_usage)。既存呼び出しは無変更で動く。
- symlink 回帰テスト(台本/casting/wav ディレクトリの置き換え→すべて
  `path_not_allowed`)が封じ込めを固定する。
- ソースビルドの前提が Go 1.25+ になる。

## Alternatives considered

1. **サーバーミント方式**(Issue 原案): `ensure_workspace(project_dir)` が
   `<project_dir>/.voice-studio-<GUID>/` を生成し所有権マーカーで再認識する。
   → 動くが儀式が過剰。「用意するのはエージェント」という原則に立てば、
   新ツール・GUID・マーカー・allowed_roots はすべて不要になる。棄却。
2. **インライン入力方式**(検討対案): `synthesize_script`/`master` に
   `script`/`casting` の内容文字列パラメータを追加し、入力の FS 共有自体を
   不要化(クラス B の入力面も解決)。→ トークンコスト(台本 30KB ≒
   1万数千トークン/呼び出し)を、クラス A には払う必要がない。データ伝達
   経路も二重化する。クラス B 対応が実需になった時の再検討案として記録。
   棄却(v1)。
3. **os.Root なしで従来の字句検査のみ**: TOCTOU・symlink に対して無力で、
   エージェント書き込み可能領域では不十分。棄却。
