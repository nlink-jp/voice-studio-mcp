# ADR-0008: ライセンス情報の収集は AIVM マニフェストから自動化し、確認は人間に残す

- **Status**: Accepted (2026-07-04)
- **Amends**: [ADR-0007](0007-license-metadata-as-data.ja.md)(方針は維持、収集手段を追加)

## Context

ADR-0007 は「エンジン API はモデルの規約を返さない」ことを前提に、
`[[speaker_metadata]]` の全手入力を要求していた。しかし実機調査(2026-07-04)で
次が判明した:

- AivisSpeech Engine 固有の `GET /aivm_models` が、インストール済み全モデルの
  **AIVM マニフェスト**を返す。マニフェストには **`license`(ライセンス全文)**、
  `description`(クレジット文言を含むことが多い)、`creators` が含まれる。
- 実際の20モデル中、17が ACML 1.0 全文、CC0 / JVNVコーパス規約 / 規約URLのみ、
  が各1(無記載も存在し得る)。
- つまり「規約情報の収集」はローカルで自動化できる。一方、規約の**解釈と承認**
  (商用可否の判断、公開用途との適合)は依然として自然文の読解であり、
  自動化すべきでない(ADR-0007 の核心は変わらない)。

10モデル×手入力という運用摩擦が現実に発生しており(パイロットで全モデル
unverified 警告)、収集の自動化には十分な動機がある。

## Decision

「**収集は自動、確認は人間**」に役割を分割する。

1. `engine.Client.AivmModels()` で `/aivm_models` を読む(ローカルのみ。
   AivisHub 等への外部アクセスは引き続きしない)。
2. ライセンスステータスを 3 値に拡張する:
   - `verified` — 人間が規約を読み `[[speaker_metadata]]` に記録済み(従来どおり)
   - `declared` — **マニフェストにライセンス全文が宣言されている**(名称は
     先頭見出し、クレジットは description の「AivisSpeech: 名前」パターンから
     機械抽出)。未確認であることを notes で明示
   - `unverified` — 宣言も記録もない
3. `list_speakers` は declared 情報を自動付与する(`/aivm_models` 不達時は
   静かに従来動作へフォールバック — VOICEVOX 等の非対応エンジンを考慮)。
4. 新サブコマンド **`licenses`** で確認ワークフローを提供する:
   - 一覧表(verified / declared / unverified の分布と次のアクション)
   - `--full <speaker_uuid>` — 全文を表示(人間が読む)
   - `--toml` — 未確認話者の `[[speaker_metadata]]` スケルトンを生成
     (`REVIEW:` ノート付き。読んで承諾したらノートを消し `commercial_use` 等を
     確定させる)

## Consequences

- 手入力は「UUID・名称・宣言ライセンス名・クレジットの転記」から
  「生成されたスケルトンの確認と穴埋め(license_url、commercial_use)」に軽減。
- `declared` は「作者がそう宣言している」以上の意味を持たない。エージェントは
  キャスティング時に declared を参考にできるが、`master` の unverified 警告は
  **verified 以外**に対して出続ける(公開ゲートは従来どおり)。
- ライセンス名・クレジットの抽出はヒューリスティック(見出し行、「」パターン)
  であり、外れても実害は「空欄が残る」に留まる。
- `/aivm_models` は応答にアイコン(base64)を含み巨大(実測147KB/20モデル)。
  構造体で必要フィールドのみ選択的にパースする。

## レジストリの置き場所(データの境界)

verified レジストリ(`[[speaker_metadata]]`)は**ユーザーデータ**であり、
ユーザー config(`~/.config/voice-studio-mcp/config.toml`)にのみ置く。
**製品リポジトリには決して同梱しない**:

1. 導入モデルは環境ごとに異なる(環境固有データ)
2. 「確認済み」は利用者自身の判断であり、リポジトリ同梱は第三者への
   法的判断の配布になる
3. 規約は時間とともに変わり得る(notes に確認日を記録するのはこのため)

なお speaker_uuid はマシンローカル ID ではなく**モデル固有のグローバル ID**
なので、レジストリは個人資産としては可搬である(別マシンに同じモデルを
導入すれば同じ UUID で一致する)。個人の dotfiles 等で config を同期・
バックアップする運用は妥当。

## Alternatives considered

- **AivisHub API からの取得**: 外部アクセスがローカル完結方針に反する。
  マニフェスト同梱の全文で十分。license_url の穴埋めのみ人間が行う。不採用。
- **規約全文の LLM 解釈で commercial_use を自動判定**: 誤判定の帰結が法的
  リスクであり、ADR-0007 の「承認は人間の責務」を崩す。不採用。
- **verified/unverified の2値のまま宣言情報を verified に混ぜる**: 「読んだ」
  事実と「書いてある」事実の区別が消え、公開ゲートが形骸化する。不採用。
